# Design: 审稿台是对红循环，不是三个模块

## Problem Statement

刘籽烨对包装/备案稿不是「审一次」。她从头到尾一个字一个字对，发现错就通知设计改、导出新 PDF，再从头对。经常性错误是漏字、少字、少空格。漏了会备案打回或印刷返工。

用户原话里的功能清单是：Excel 审 PDF、2D 转 3D、历史记录。真正的工作不是这三块并列。

## Demand Evidence

- 验收人有名字：刘籽烨。后果是备案打回或印刷返工，不是「有了系统比较方便」。
- 现状行为已发生：逐字对 → 通知设计 → 新 PDF → 再逐字对。这是每周都在付的时间，不是设想。
- 尚未验证：她有没有在现有网页上完成过一单真签；工具消失她会不会当晚加班。8/31 要用一单真稿补上这条。

## Status Quo

1. 左右开 Excel 与 PDF（或等价物），逐字对。
2. 只审不改。把错通知设计。
3. 设计改完出新 PDF。
4. 她再全文逐字对一遍。

对手是这条土办法，不是 Esko。印刷行当把第 4 步叫「二校 / 对红」：核对上一轮红笔是否改掉，并防改稿带出新错。

## Target User & Narrowest Wedge

- 人：刘籽烨，内部审核，不改稿。
- 楔子：同一任务上能放第二份 PDF，只问「上次那些漏字/少字/空格改掉了没有」，并给出可转发给设计的改稿清单。
- 任务列表按品名能找到她签过的单。这就是 8/31 的「历史」。
- 领导按 SKU 抽查后做。
- 2D 转 3D 仍是打样台，不进对字循环，8/31 不接线。

## Constraints

- 飞书身份 + 白名单。不买云。杭州 Windows 生产。
- 不重写审核引擎和 3D CLI，在现有 tasks 上长对红。
- 机审只标疑点，人写结论。禁止「AI 已过审」。
- 视觉已锁：紫白顶栏、图上钉、蝴蝶 logo。见 `DESIGN.md`。
- 密钥和真稿不进 git。

## Premises

1. 8/31 产品是籽烨的对字循环，不是三个并列模块。 — 同意
2. 「历史」分两层：本单版本/对红必须有；跨单 8/31 只做按品名找她签过的单；领导抽查后做。 — 同意（用户否决了「完全不做跨单」，接受薄检索）
3. 机审要能标漏字/少字/少空格，不能只做字段是否相等。 — 同意。8/31 验收条是金标样本标「待人工确认」，不是全字段检出率。
4. 她只通知设计，产出是可转发的改稿清单。 — 同意
5. 2D 转 3D 是另一张台。 — 同意

否决：单独「历史中心」模块（用户要搜旧单，但选了任务即档案，不单开第三产品）。

## Approaches Considered

### Approach A: 最小楔子
一校 + 清单 + 再传 PDF 对红 + 任务列表搜品名。有版本，UI 仍像多一个入口。

### Approach B: 理想架构
正式版本对象、字符 diff、飞书推设计、领导检索、3D 共用稿号。8/31 做不完。用户未选。

### Approach C: 任务即档案（选定）
不单独做历史页。任务就是档案。对红 = 同一任务上的下一份 PDF。搜品名 = 搜任务。

## Recommended Approach

Approach C。禁止 `/history` 和名为「历史中心」的页。任务页里「上一版 / 这一版」切换允许。

### 阻塞门

没有书面许可进机的「旧 PDF + 新 PDF + 她发给设计的那段话 + 二校新发现的漏字/少字/空格」，**不对红、不加严空格引擎**。先人工对这一对，记下「只做字段对照会漏什么」。

### 8/31 拆两层

- **P0（章程，不可再缩）：** 她在符合 `DESIGN.md` 的审稿台上走完一单一校并写出结论。先把 React 接到已有 decide/complete。
- **P1（本稿，有金标才做）：** 同一单再传第二份 PDF，默认只复检上一轮 issue。

### 状态（对外文案）

```
对照中 → 待审核 →（一校有 issue）等新稿
                 →（一校零 issue）已签字
等新稿 →（她上传新 PDF）对红中 → 待审核（对红）
对红后：仍可签字（结论写清未改项）。8/31 不收第三份 PDF，不覆盖 v1/v2。
```

对外文案对照现有字段（不要第三套枚举）：

| 她看见 | 内部 |
|---|---|
| 对照中 | `in_review` |
| 待审核 | `in_review` + 有 hits |
| 等新稿 | `in_review` + round=1 + 有 issue + 无 v2 |
| 对红中 | `in_review` + round=2 + 正在跑 |
| 已签字 | `completed` |

签字 = 她提交人话结论 + 名字 + 时间，走现有 `complete()`，对外写「已签字」，禁止「终审完成 / AI 已过审」。  
一校有 issue 时**禁止**调用 `complete()`。文案用「待设计改稿」。

### 数据（不要 versions[]）

每个 task 固定：

- Excel 一份，一校后锁死
- `artwork_v1.pdf` / `artwork_v2.pdf` 两份，不覆盖；页面分 `pages/v1/` `pages/v2/`
- `round` = 1 | 2
- `product_name`：创建时从确认单写入，没有则手填，禁止默认「Excel↔包装」
- `open_issues[]` 稳定键：`field + expected_text`（可选 page）+ `her_note` + `observed_text`（她标 issue 时的错误形态）  
  **不要用**会重生的 hit id。判定读 `expected_text` 与 `observed_text`。

8/31 只允许她本人在「等新稿」时往同一 task 再传一份 PDF。传错稿（页数/品名对不上）拒绝并保留 v1。

### 对红判定（死规则）

新 PDF 重跑后，按稳定键回贴，不按 hit id：

1. 规范化后仍含「人判错误形态」→ 仍在
2. 含「人判期望形态」且不含错误形态 → 已改
3. 两者都找不到 → `待人工确认`（禁止标一致）

bbox 只展示，不作判定。定位失败的项留在任务上，不要丢。  
对红回贴用**保留空白**的比较（独立 pass 的文本），不要拿去空白后的 `normalize()` 判「仍在 / 已改」。字段相等对照维持原 `normalize()`。  
默认队列**只**复检上一轮 issue。全量 hits 仍可看，不隐藏。旧新 PDF 全量文本 diff **8/31 不做**（防新错标到 9 月）。

### 漏字 / 少空格

8/31 只认：金标样本上标「待人工确认」，禁止写成确定一致。  
做成**独立 pass**，只输出疑点，不回写已有「一致」。不要改 `fields.normalize()` 的全局去空白。

### 改稿清单

人判增加可选 `note`。清单只含 `decision=issue`。提供「复制改稿清单」纯文本（字段、原文、页码、她的话）。8/31 不强制飞书机器人。

### 列表即档案

`GET /api/tasks` 用已有 `mine=` + 新 `q` 搜 `product_name|title`。不要新路由。

### 实现顺序

1. Vite build，`GET /` 改挂 `apps/web/ui/dist`（main.py:2716-2721）。旧 `frontend/` 不再当验收入口。
2. 同一 PR：`theme.ts` `colorPrimary=#722ED1`，拆 220px 侧栏，顶栏蝴蝶+审稿台/打样台；审稿页接 decide（含 note）和 complete。
3. 新建品名必填，禁止默认「Excel↔包装」；写入 `product_name`；`GET /api/tasks?q=`。
4. 复制改稿清单；complete 有 issue 也允许，飞书文案「待设计改稿」不是「终审完成」。
5. pytest 六条（见测试计划）。有金标后再做 P1 对红。

打样台顶栏「内部准备中」只遵守 `DESIGN.md`，不是本期对红交付。

复用：tasks API、hits、人判、同步对照；新 PDF 沿用「正在对照，请稍候」。
