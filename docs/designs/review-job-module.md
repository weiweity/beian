## Problem Statement

前端 v0.10.2 已交。对外 HTTP 已是 Hono `:8787`，不是白纸。缺的是长作业合同：对照约 40 秒、打样约 4 分钟，现在同步堵住请求；打样作业在内存 Map，重启即丢。刘籽烨已催上线，因为对字加班看不到头。同时工程师要能加功能、适合 AI coding，峰值约 10 人、偶尔 3 人同时开跑。

不是从零写后端。不是把 FastAPI 38 条路由搬进产品。不是 AI 中转台。

## Demand Evidence

- 人：刘籽烨。展示后催「啥时候上线」。
- 原话：「没有的话，一眼望不到的头的加班。」
- 行为已发生：双屏逐字对、飞书通知设计、新 PDF 再对；新品几乎都要折盒子交差备案图。
- 尚未验证：她有没有在现网页上独立签完一单真稿。

## Status Quo

她：左右 Excel+PDF → 飞书打字给设计 → 新稿再对 → 打印手折拍照交差。
系统：`POST /api/tasks/upload` 等 `python -m app.cli compare` 结束才返回；打样 `startMockup` 同步等到 Blender 结束，忙则 409；飞书只在签字 `complete` 时推。
工程师怕以后加不了功能，想要「二次开发平台」。

## Target User & Narrowest Wedge

- 第一期验收人仍是刘籽烨。10 人是容量，不是这周用户名单。
- 楔子：她能离开页面，对照结束后被叫回来签字。
- 用户选择把楔子做成**深作业模块**（对照 / 对红 / 打样同一套语义），而不是只改对照。8/31 验收仍只看审稿台一校真签；打样进同一模块，但不对业务承诺 Windows 3D。

## Constraints

- 唯一 HTTP：`apps/web/server` `:8787`。Python 只走 `python -m app.cli`。不启动 uvicorn。
- 不重写对照引擎和 3D 流水线。缺 Blender 必须明确失败。
- 8/31 不引入 Redis、BullMQ、SQLite、通用队列中间件、WebSocket。
- 机审只标疑点。禁止「AI 已过审」。不能取消的作业不做取消按钮。
- 密钥和真稿不进 git。杭州 Windows 才是生产。
- 二次开发形状：加功能 = 一个 Hono 产品动作 + 一条 worker 命令。不按页拆 package。

## Premises

1. 这周交货是籽烨能在 `:8787` 签完一单。10 人是容量约束，不是新产品。
2. **（Codex 后写硬）** 排队落在已有 task / mockup JSON 上，不引入 Redis / BullMQ / SQLite。必须同时有：原子写入（tmp+rename）、单进程 dispatcher、重启把 `running` 回收、作业不重复跑、飞书通知幂等。JSON 没有这些语义就不是队列。
3. 二次开发 / 适合 AI coding = 加深 `jobs` 模块，不迁 FastAPI 目录、不按页面建包。
4. 进度来自 worker 真实阶段。没有阶段证据就不画百分比。
5. 打样可进同一作业模型，8/31 验收仍只有审稿台。

## Cross-Model Perspective

Codex 冷读：最强版本是「人工终审驾驶舱」，不是自动审批。最关键原话是加班那句。挑战前提 2：裸 JSON 不是队列。48 小时原型仍用 JSON+rename+单槽 dispatcher，跳过 Redis / 打样业务开放 / FastAPI 迁移。用户同意把前提 2 写硬，并选择比 Codex 原型更宽的深作业模块（把对红和打样收进同一模块）。

## Approaches Considered

### Approach A: 最小异步对照

只让上传立即返回，1 槽跑对照。打样仍 409。

否决：挂机没有对照完成通知，3 人排队合同不清。

### Approach B: 深作业模块（选定）

对照 / 对红 / 打样共用内部 Job：槽位、阶段、持久化、崩溃回收、通知幂等。HTTP 资源不新增第四套，仍是 tasks 与 mockups。

### Approach C: 48 小时驾驶舱

只做对照可挂机 + 真实阶段 + 结束飞书。打样整周不动。

否决：用户要三张长作业同一套语义，否则以后加功能还是两套。

## Recommended Approach

加深一个模块：`apps/web/server/src/jobs.ts`。`workers.ts` 继续只负责 spawn + 超时 + 读 stdout；`jobs.ts` 调用它，独占 FIFO / 槽位 / 回收 / 通知 / 把结果写回任务文件。两边都不得各自杀进程。

签名：

```
enqueue({ kind: "compare"|"rework"|"mockup", id: string }): Task|Mockup  // 落盘 queued，立即返回
reclaimOnBoot(): void  // index.ts 在 serve() 之前调用
```

两条独立 FIFO，不是一条混扫：

- OCR 队：`tasks/*.json` 里 `job_kind` 为 compare|rework 且 `job_status=queued`，按 `created_at` 升序，槽=1。
- Blender 队：`mockups/{id}/job.json` 里 queued，按 `created_at` 升序，槽=1。

泵：`tryStart()` 在这些时刻各调一次：`enqueue` 返回前、任一作业终态之后、`reclaimOnBoot` 末尾、活 pid 等到退出并写完终态之后。OCR 槽空则取 OCR 队头；Blender 槽空则取打样队头。两队互不等待。杀 Node 再启动不得等到下一次 POST 才跑队。

### 唯一写者

Python `cli.py` **不再** `save_task`。对照/对红 CLI 只把结果 JSON 打到 stdout 最后一行；`jobs.ts` 在进程退出后合并 `hits` / `pages` / `status`，并保留 `job_*`。阶段行是 stderr 或 stdout 上单独的 `STAGE <name>`，`workers.ts` 必须边跑边读，不能等 close 再吐给 UI。

任务文件写入一律 tmp + replace（Windows 上 dest 已存在时 POSIX rename 会失败；对齐 Python `os.replace`）。禁止 `jobs.ts` 和 CLI 同时 replace 同一文件。

`POST /api/uploads` 只落当前用户的待开工回执，不建任务。`POST /api/tasks/start` 或对红路由负责领取文件、**第一次** `saveTask`（`status=comparing`、`job_status=queued`、对红时写 `status_before_job`）、然后 `enqueue`。入队成功之后，这个 tid 只允许 `jobs.ts` 再写。路由层不得在 worker 跑着时再 `saveTask`。

打样持久化：`DATA_DIR/mockups/{id}/job.json`。内存 Map 只作热缓存，开机以磁盘为准。

打样写回：`runPackaging` 退出码 0 → 现有 `collectOutputs` 填 `files`（只公开 key/name；白底只收 `front_right` / `back_left`，不要把 `ai-raster` 或 PPT 质检 PNG 算进去；另收 `glb` / `ppt` / `sheet`），`status=done`，`job_status=succeeded`。非 0 或超时 → `status=failed`，`job_status=failed`，`job_error` 截 800 字。不读 packaging 的内部目录当 HTTP 合同。

### HTTP 合同（不新增 `/api/jobs`）

GET 必须走 `publicTask` / `publicMockup`，剥掉 `job_pid`、磁盘 `path`。

| 方法 | 路径 | 变什么 |
|---|---|---|
| POST | `/api/uploads` | 限流并暂存当前用户的 Excel+PDF 或 `.ai`，返回有时限、有额度的回执；不建任务、不入队。 |
| GET / DELETE | `/api/uploads` / `/api/uploads/:id` | 列出自己的待开工回执，或放弃回执并清掉暂存文件。 |
| POST | `/api/tasks/start` | 领取回执、写盘、`task.status=comparing`、`job_status=queued`、入队、立即返回；同一 `source_receipt` 重试返回原任务。 |
| POST | `/api/tasks/:tid/rework` | kind=`rework`。对红门不变。已有 `job_status` 为 queued/running → 409「对红还在排队或正在跑」。 |
| GET | `/api/tasks` / `/api/tasks/:tid` | 多返回公开作业字段。`board` 仍只看 `task.status`。 |
| POST | `/api/mockups/start` | 领取 `.ai` 回执；本机没有 Blender / Illustrator → **当场失败**（不入队、不事后飞书）。依赖齐全则入队，忙时仍是 `queued`；同一 `source_receipt` 重试返回原打样单。 |
| GET | `/api/mockups` / `/:id` | 读 `job.json`。无 `path`。mockup `status` 仍用现有 `queued\|running\|done\|failed`，不要改成 succeeded。 |
| GET | `/api/mockups/:id/files/:key` | 只给白底 `front_right`/`back_left`、GLB、PPT、打样单 PDF（`sheet`）。预览 inline，`?download=1` 才附件。`ai-raster`/PPT 质检图或坏 PNG → 415。流式读盘，不一次塞进内存。缺 PPT 或 PDF 时 404，不要假装能下。 |
| GET | `/api/health` / `/api/status` | 公网 health 只给发版探活所需字段；登录后的 status 才给准确作业槽和飞书状态。 |

鉴权、设置、账单、飞书登录、页图、`decision` 不变。`complete` 签字门忽略工艺说明 / 颜色要求 / 版本号 / 更新内容的 pending（只认字段名开头，避免「备案版本号」「执行标准版本号」被误杀）。不迁 FastAPI 的 gold / backup / ai-review / report.pdf / presets。

`compareBookkeeping` 从 upload/rework 的 try/catch 挪到作业终态（`jobs.ts` 里 succeeded/failed 时记一笔）。

### 状态矩阵

不要把 `queued` 写成 `task.status`。看板和 WaitCard 认现在的词。

| 事件 | task.status | job_status | board | WaitCard |
|---|---|---|---|---|
| 上传已收 | comparing | queued | comparing | 是，「前面还有 N 单」 |
| worker 开工 | comparing | running | comparing | 是，大约 40 秒 + stage |
| 对照成功 | pending_review | succeeded | review | 否 |
| 对照失败/超时 | compare_failed | failed | comparing | 否 |
| 对红已收 | comparing | queued（kind=rework） | comparing | 是，「对红中」 |
| 对红成功 | in_review | succeeded | review | 否 |
| 对红失败/超时 | 回到 `status_before_job`（入队前写入的 pending_review 或 in_review），v1 hits 不动 | failed | review | 否 |

对红失败仍可签字。不得写成 `compare_failed`。失败后允许同一 tid 再入队。

### 作业字段

公开（GET 给 UI）：`job_kind` `job_status` `job_stage` `job_stage_label` `job_eta_s` `job_error` `job_started_at` `job_finished_at` `queue_ahead`（queued 时前面还有几单）

内部不返回：`job_pid` `notify_job_id` `reclaim_count`

`job_stage` 白名单与汉字：`render_pdf` 出图、`ocr` 认字、`match` 对照、`blender` 打样、`export` 导出。未知 STAGE 忽略，不编百分比。

`job_eta_s` 只在 `running` 时给常数：对照/对红 40，打样 240。queued 只用 `queue_ahead`，禁止对排队中的单显示 40 秒。没有 STAGE 也用这条常数，不画百分比。

### 槽位与 Windows 回收

- OCR 槽 **1**（compare+rework）。3 人同时上传 = 1 running + 2 queued。
- Blender 槽 **1**，与 OCR 独立。
- FIFO，不按用户公平。同一 tid 在 queued/running 时不可再入队。

杭州生产是 Windows。`serve()` 杀掉 Node 时 Python/Blender 常常还活着。开机 `reclaimOnBoot`：

1. `task.status` 已是 pending_review / in_review / completed → `job_status=succeeded`，**不准重跑**。
2. 已是 compare_failed 或 mockup failed 且有 `job_finished_at` → 不动。
3. 仍 queued → 留在队里。
4. running 且 pid 仍是这个作业（pid + `job_started_at` + 命令行对得上）→ **占住槽，等这个进程自己退出，不准开第二条**。对照/对红：退出后读不到结果 JSON → `failed`，`job_error=对照中断`，不再入队。打样：退出码 0 且能 `collectOutputs` 到至少 1 个文件 → `done`/`succeeded`；否则 `failed`，`job_error=打样中断`。
5. running、pid 已死、未超时、`reclaim_count < 1`、且仍在跑的对外状态（对照 `comparing` / 打样 `running`）→ 改 queued，`reclaim_count++`。
6. running、pid 已死、已超时 → failed，`job_error=超时`。
7. running、pid 已死、未超时、但 `reclaim_count >= 1` → failed，`job_error=对照中断` 或 `打样中断`。不得留在 running。

Windows 上 spawn 必须进 Job Object，Node 退出时杀掉子进程树。做不到 Job Object 的开发机（Mac）至少 SIGTERM 进程组。证明前提 2：双人提交、杀 Node 再启动、飞书对照完成只一条。

### Worker

- 对照 / 对红：`python -m app.cli compare|rework`，最后一行结果 JSON，过程中 `STAGE render_pdf|ocr|match`。不搬 `fields.py`。确认单底部工艺说明 / 颜色要求 / 版本号 / 更新内容走 `skip_sheet_field`（字段名开头），不进机审。
- 打样：`workers/packaging`。POST 时已确认 Blender；跑到一半消失 → failed，写清。stderr 打 `STAGE render_pdf|blender|export`（出图/打样/导出）。入队后 `job_stage` 从 `render_pdf` 开始，不是 `blender`。平面出图用 pymupdf（对照同一 Python），不靠 qlmanage。先读刀线/刀版还原切面；密折痕先密后疏试间距；没有刀线才回退已登记 JSON，不能硬套方盒。PPT 先用两张白底写 OOXML，不依赖 Node；写不出才试演示文稿运行时（stderr `PPT 跳过`）。两张白底合成一页 PDF。缺 PPT/PDF 时白底图和 GLB 仍 `done`/`succeeded`，不要把整单判成「Node不存在」。
- 超时：对照 180s、打样 420s（已有）。超时 = failed，回收槽。
- 取消：不做。

### 通知

- 对照 / 对红作业成功或失败各一条飞书。收件人 = 现有 `FEISHU_OPEN_ID`（籽烨），不是 `task.owner`。深链对照 `/review/:id`，打样 `/mockup/:id`，不要拼 `/?task=`。
- 打样飞书：模块里做得到，8/31 演示不作为验收。
- 签字 `complete` 仍发现有文案。
- 幂等键：`{tid}:{job_kind}:{job_started_at}`（离开 queued 时写死）。**先写 `notify_job_id` 再 `sendText`**。发送失败保留键、打日志：至多一次，不补发。
- 文案：「某某精华 对照完了，来签字。」失败带 `job_error`。

### UI 合同（三处，不是后补）

轮询已有 GET，间隔 2.5s（现成）。

- `NewTaskPage`：先上传得到回执，再调用 `/api/tasks/start`；开始接口立即返回后进入核对页。核对页见 `job_status in {queued,running}` 或 `status===comparing` 就上 WaitCard。
- `ReviewPage`：对红 POST 返回 queued 时不要 toast「已对照第二份 PDF」；WaitCard 增加「对红」文案。
- `MockupPage` / `MockupJobPage`：打样台只交稿和列单。点进度或已出图进打样单；进行中是 WaitCard，完成一屏三图：正面+侧面、反面+侧面、GLB；每张图右上角下载；页头「下载 PPT」（没写成仍显示，点了出「PPT 没写成，白底仍可下」），不提供 PDF 下载入口；点下载底部提示不挡操作；GLB 全屏居中；截图时下载钮藏起来；全屏被拒出「全屏打不开」。不要死等 POST；打样单里轮询 GET `/api/mockups/:id`。`status=done|failed` 不当等待卡。地址 `/mockup`、`/mockup/new` 与 `/mockup/:id`。审稿台看板 `/reviewup`，工作台 `/reviewup/new`，核对页仍 `/review/:id`。
- `WaitCard`：吃 `job_stage` / `job_stage_label`、`job_eta_s`、`queue_ahead`。queued 显示「前面还有 N 单」。
- `TasksPage`：任一 `board==comparing` 时轮询 `/api/tasks`，否则排队卡片会停在旧状态。审稿台四栏统一用紧凑明细；对照中首行显示品名和由真实阶段映射出的粗粒度百分比，下一行只放日期。WaitCard、历史行和侧栏仍用 `liveJobLine` 写阶段和大约还要，不画假精确百分比。
- 侧栏：`liveNavPulse` 看登录后 `/api/status` 的 jobs 槽；审稿台/打样台作业在跑时有圆点。离开核对页再回看板，仍能看到阶段。
- `HistoryPage`：进行中的审稿/打样也列；行上写 `liveJobLine`（阶段 · 大约还要 / 前面还有 N 单），不要百分比。点进去仍是 WaitCard / 打样单。有 `processing` 行就 2.5s 轮询。

### 二次开发怎么加功能

新能力只允许：Hono 一个产品动作；worker 一条命令。  
禁止：新端口、Python HTTP、按侧栏 tab 新建 package、把 FastAPI 路由当产品清单。

`workers.ts` = 命令、spawn、超时、STAGE 流。  
`jobs.ts` = FIFO、槽、回收、通知、唯一写回任务文件。

## Open Questions

- 百度 OCR 实际 QPS 未知。默认对照槽=1；有证据能稳跑 2 再加，不在本文放开。
- 10 人名单里除籽烨外，第一周还有谁登录：写不出则验收仍按 1 人。
- 对照完成飞书 vs 只在失败时飞书：默认成功失败都发；她嫌吵再改成只失败。

## Success Criteria

8/31 演示（审稿台）：

- 籽烨能不盯屏完成一单：上传 → 离开 → 飞书叫回来 → 人判 → 写下结论签字。
- 3 个上传同时进来，同时只跑 1 条对照，另外 2 条 queued，看板都在「对照中」。
- 杀掉 Node 再启动：没有永久「对照中」；通知不重复。
- 失败任务不能签字。对红失败仍可签字。
- 界面不出现「AI 已过审」。没有假取消。
- `apps/web/ui/src/api.ts` 不新增第四套资源名。
