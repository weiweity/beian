## Problem Statement

前端 v0.10.2 已交。对外 HTTP 已是 Hono `:8787`，不是白纸。缺的是长作业合同：对照约 40 秒、打样约 4 分钟，现在同步堵住请求；打样作业在内存 Map，重启即丢。刘籽烨已催上线，因为对字加班看不到头。同时工程师要能加功能、适合 AI coding，峰值约 10 人、偶尔 3 人同时开跑。

不是从零写后端。不是把 FastAPI 38 条路由搬进产品。不是 AI 中转台。

## Demand Evidence

- 人：刘籽烨。展示后催「啥时候上线」。
- 原话：「没有的话，一眼望不到的头的加班。」
- 行为已发生：双屏逐字对、飞书通知设计、新 PDF 再对；新品几乎都要折盒子交差备案图。
- 尚未验证：她有没有在现网页上独立签完一单真稿。

## Status Quo

她：左右 Excel+PDF → 飞书打字给设计 → 新稿再对 → 打印手折拍照交差。
系统：`POST /api/tasks/upload` 等 `python -m app.cli compare` 结束才返回；打样 `startMockup` 同步等到 Blender 结束，忙则 409；飞书只在签字 `complete` 时推。
工程师怕以后加不了功能，想要「二次开发平台」。

## Target User & Narrowest Wedge

- 第一期验收人仍是刘籽烨。10 人是容量，不是这周用户名单。
- 楔子：她能离开页面，对照结束后被叫回来签字。
- 用户选择把楔子做成**深作业模块**（对照 / 对红 / 打样同一套语义），而不是只改对照。8/31 验收仍只看审稿台一校真签；打样进同一模块，但不对业务承诺 Windows 3D。

## Constraints

- 唯一 HTTP：`apps/web/server` `:8787`。Python 只走 `python -m app.cli`。不启动 uvicorn。
- 不重写对照引擎和 3D 流水线。缺 Blender 必须明确失败。
- 8/31 不引入 Redis、BullMQ、SQLite、通用队列中间件、WebSocket。
- 机审只标疑点。禁止「AI 已过审」。不能取消的作业不做取消按钮。
- 密钥和真稿不进 git。杭州 Windows 才是生产。
- 二次开发形状：加功能 = 一个 Hono 产品动作 + 一条 worker 命令。不按页拆 package。

## Premises

1. 这周交货是籽烨能在 `:8787` 签完一单。10 人是容量约束，不是新产品。
2. **（Codex 后写硬）** 排队落在已有 task / mockup JSON 上，不引入 Redis / BullMQ / SQLite。必须同时有：原子写入（tmp+rename）、单进程 dispatcher、重启把 `running` 回收、作业不重复跑、飞书通知幂等。JSON 没有这些语义就不是队列。
3. 二次开发 / 适合 AI coding = 加深 `jobs` 模块，不迁 FastAPI 目录、不按页面建包。
4. 进度来自 worker 真实阶段。没有阶段证据就不画百分比。
5. 打样可进同一作业模型，8/31 验收仍只有审稿台。

## Cross-Model Perspective

Codex 冷读：最强版本是「人工终审驾驶舱」，不是自动审批。最关键原话是加班那句。挑战前提 2：裸 JSON 不是队列。48 小时原型仍用 JSON+rename+单槽 dispatcher，跳过 Redis / 打样业务开放 / FastAPI 迁移。用户同意把前提 2 写硬，并选择比 Codex 原型更宽的深作业模块（把对红和打样收进同一模块）。

## Approaches Considered

### Approach A: 最小异步对照

只让上传立即返回，1 槽跑对照。打样仍 409。

否决：挂机没有对照完成通知，3 人排队合同不清。

### Approach B: 深作业模块（选定）

对照 / 对红 / 打样共用内部 Job：槽位、阶段、持久化、崩溃回收、通知幂等。HTTP 资源不新增第四套，仍是 tasks 与 mockups。

### Approach C: 48 小时驾驶舱

只做对照可挂机 + 真实阶段 + 结束飞书。打样整周不动。

否决：用户要三张长作业同一套语义，否则以后加功能还是两套。

## Recommended Approach

加深一个模块：`apps/web/server/src/jobs.ts`。`workers.ts` 继续只负责 spawn + 超时 + 读 stdout；`jobs.ts` 调用它，独占 FIFO / 槽位 / 回收 / 通知 / 把结果写回任务文件。两边都不得各自杀进程。

签名：

```
enqueue({ kind: "compare"|"rework"|"mockup", id: string }): Task|Mockup  // 落盘 queued，立即返回
reclaimOnBoot(): void  // index.ts 在 serve() 之前调用
```

两条独立 FIFO，不是一条混扫：

- OCR 队：`tasks/*.json` 里 `job_kind` 为 compare|rework 且 `job_status=queued`，按 `created_at` 升序，槽=1。
- Blender 队：`mockups/{id}/job.json` 里 queued，按 `created_at` 升序，槽=1。

泵：`tryStart()` 在这些时刻各调一次：`enqueue` 返回前、任一作业终态之后、`reclaimOnBoot` 末尾、活 pid 等到退出并写完终态之后。OCR 槽空则取 OCR 队头；Blender 槽空则取打样队头。两队互不等待。杀 Node 再启动不得等到下一次 POST 才跑队。

### 唯一写者

Python `cli.py` **不再** `save_task`。对照/对红 CLI 只把结果 JSON 打到 stdout 最后一行；`jobs.ts` 在进程退出后合并 `hits` / `pages` / `status`，并保留 `job_*`。阶段行是 stderr 或 stdout 上单独的 `STAGE <name>`，`workers.ts` 必须边跑边读，不能等 close 再吐给 UI。

任务文件写入一律 tmp + replace（Windows 上 dest 已存在时 POSIX rename 会失败；对齐 Python `os.replace`）。禁止 `jobs.ts` 和 CLI 同时 replace 同一文件。

`POST /api/uploads` 只落当前用户的待开工回执，不建任务。`POST /api/tasks/start` / `/api/mockups/start` 先按 `owner + source_receipt` 串行，再把回执 JSON 原子改名成 `.take` durable claim；文件准备和**第一次**任务落盘完成后才删除 claim 与暂存文件。任务落盘前失败就把 claim 原子退回；Node 在 claim 与任务落盘之间退出时，下一次启动会恢复回执，任务已经按 `source_receipt` 落盘时则完成清理。用户主动放弃时先把 claim 原子改成 `.take.discard` 删除墓碑，进程退出后只会继续删除，不会还原回执。同一回执的并发或响应丢失重试必须收敛到同一任务，不得短暂误报“上传已过期”。过期响应使用稳定 `code=upload_receipt_expired`，前端不得匹配中文文案。结构确认同样以持久化状态为幂等事实：重叠执行仍返回 409，但首次确认已落盘后的响应丢失重试直接返回当前打样单，不重复运行结构 worker。对照任务第一次 `saveTask` 写 `status=comparing`、`job_status=queued`；入队成功之后，这个 tid 只允许 `jobs.ts` 再写。路由层不得在 worker 跑着时再 `saveTask`。

打样持久化：`DATA_DIR/mockups/{id}/job.json`。内存 Map 只作热缓存，开机以磁盘为准。

### 权限与团队协作

`users.json` 只配置 `admin/reviewer/viewer`，不存页面级权限数组。Hono 把权限拆为三层：所有已登录角色都可读取、下载团队打样单和结构预览；结构确认必须具备独立 `confirm_structure` 能力，现已授予 `admin` / `reviewer` / `viewer`；删除继续经过对象所有权校验，`reviewer` 只能删本人已结束打样单，`admin` 可删全部，`viewer` 无删除能力。选层是第四层：`POST /api/mockups/:id/structure/input` 只给 `admin`，即使审稿员有 `confirm_structure` 也 403；非管理员详情省略 `structure_input`。审稿单仍保持原有所有者隔离。团队共享序列化必须再次脱敏旧 worker 错误里的本机绝对路径、客户稿件名和疑似凭据，只返回短摘要；列表不得为轮询读取完整结构预览。UI 只消费 `/api/auth/me.perms` 控制动作可用性，服务端继续作为最终授权边界。

打样写回：`runPackaging` 退出码 0 → 现有 `collectOutputs` 填 `files`（只公开 key/name；白底只收 `front_right` / `back_left`，不要把 `ai-raster` 或 PPT 质检 PNG 算进去；另收 `glb` / `ppt` / `sheet`，以及恰好名为 `panel_{front,back,right,left,top,bottom}.png` 的印刷面 `read_*`），`status=done`，`job_status=succeeded`。旧单 `job.files` 没有 `read_*` 时，详情读取和文件接口按磁盘现有 panel PNG 补上，不重跑 Blender。非 0 或超时 → `status=failed`，`job_status=failed`，内部 `job_error` 截 800 字；对外读取必须再走团队共享脱敏和摘要边界。不读 packaging 的内部目录当 HTTP 合同。

### 状态矩阵

不要把 `queued` 写成 `task.status`。看板和 WaitCard 认现在的词。

| 事件 | task.status | job_status | board | WaitCard |
|---|---|---|---|---|
| 上传已收 | comparing | queued | comparing | 是，「前面还有 N 单」 |
| worker 开工 | comparing | running | comparing | 是，大约 40 秒 + stage |
| 对照成功 | pending_review | succeeded | review | 否 |
| 对照失败/超时 | compare_failed | failed | comparing | 否 |
| 对红已收 | comparing | queued（kind=rework） | comparing | 是，「对红中」 |
| 对红成功 | in_review | succeeded | review | 否 |
| 对红失败/超时 | 回到 `status_before_job`（入队前写入的 pending_review 或 in_review），v1 hits 不动 | failed | review | 否 |

对红失败仍可签字。不得写成 `compare_failed`。失败后允许同一 tid 再入队。

### 作业字段

公开（GET 给 UI）：`job_kind` `job_status` `job_stage` `job_stage_label` `job_eta_s` `job_error` `job_started_at` `job_finished_at` `queue_ahead`（queued 时前面还有几单）

内部不返回：`job_pid` `notify_job_id` `reclaim_count`

`job_stage` 白名单与汉字：`structure` 正在出图、`illustrator_opening` 打开稿件、`illustrator_inventory` 盘点图层、`illustrator_saving_full_pdf` 保存整页 PDF、`illustrator_saving_artwork_pdf` 保存印刷 PDF、`illustrator_writing_result` 写出结构、`illustrator_closing` 关闭文档、`render_pdf` 出图、`ingest` 识稿、`ocr` 认字、`layout` 分区、`match` 对照、`blender` 打样、`export` 导出。未知 STAGE 忽略，不编百分比。审稿台粗粒度进度按这个顺序单调前进。打样结构识别阶段对外写「正在出图」或上述中文 Illustrator 阶段，不要再写「识别结构」。

`job_eta_s` 只在 `running` 且确有常数预算时给出：对照/对红 40，非结构打样 240。结构 `illustrator_*` 阶段不写 `job_eta_s`。queued 只用 `queue_ahead`，禁止对排队中的单显示 40 秒。没有 STAGE 才用上述常数，不画百分比，也不编造 120 秒。

### 槽位与 Windows 回收

- OCR 槽 **1**（compare+rework）。3 人同时上传 = 1 running + 2 queued。
- Blender 槽 **1**，与 OCR 独立。
- FIFO，不按用户公平。同一 tid 在 queued/running 时不可再入队。打样重试除外：先杀掉当前 worker，确认已退出再改 queued；杀不掉或还在启动就 409，避免杭州单槽叠跑。

杭州生产是 Windows。`serve()` 杀掉 Node 时 Python/Blender 常常还活着。开机 `reclaimOnBoot`：

1. `task.status` 已是 pending_review / in_review / completed → `job_status=succeeded`，**不准重跑**。
2. 已是 compare_failed 或 mockup failed 且有 `job_finished_at` → 不动。
3. 仍 queued → 留在队里。
4. running 且 pid 仍是这个作业（pid + `job_started_at` + 命令行对得上）→ **占住槽，等这个进程自己退出，不准开第二条**。对照/对红：退出后读不到结果 JSON → `failed`，`job_error=对照中断`，不再入队。打样：退出码 0 且能 `collectOutputs` 到至少 1 个文件 → `done`/`succeeded`；否则 `failed`，`job_error=打样中断`。
5. running、pid 已死、未超时、`reclaim_count < 1`、且仍在跑的对外状态（对照 `comparing` / 打样 `running`）→ 改 queued，`reclaim_count++`。打样若桌面 Agent 心跳 busy 且本单需要 Illustrator：保持 queued/running，不准 reclaim 成失败，也不领第二张 AI 单。
6. running、pid 已死、已超时 → failed，`job_error=超时`。
7. running、pid 已死、未超时、但 `reclaim_count >= 1` → failed，`job_error=对照中断` 或 `打样中断`。不得留在 running。

Windows 上 spawn 必须进 Job Object，Node 退出时杀掉子进程树。做不到 Job Object 的开发机（Mac）至少 SIGTERM 进程组。证明前提 2：双人提交、杀 Node 再启动、飞书对照完成只一条。

### Worker
